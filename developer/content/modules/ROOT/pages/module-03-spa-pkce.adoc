= Module 3: A SPA with PKCE
:navtitle: 3. A SPA with PKCE

*Time:* 45 minutes, including about 10 to start your workspace +
*Before you start:* Module 2, with all three patterns signing in +
*By the end, you can:* configure the authorization code flow with PKCE in a browser app; keep its tokens in memory, out of browser storage; refresh an access token before it expires

== Why it matters

A browser app is a *public* client: anything shipped to a browser can be read,
so it cannot keep a secret. Two things protect its sign-in and its tokens:

* **PKCE.** For each sign-in, the app makes a one-time secret, sends a hash of
  it to Keycloak, and later proves it knows the secret when it redeems the
  sign-in code. A code stolen on the way back is useless without it.
* **Where the tokens live.** Any script on the page can read
  `localStorage`, and it outlives the tab. Tokens held in JavaScript memory
  vanish when the tab closes and are harder to reach.

Access tokens here last five minutes, so the app must also get a new one
before the old one expires, without making the user sign in again.

The starter is the lab's SPA with all three of these broken. Each defect is
marked with an `ANTI-PATTERN` comment, as every starter in this lab is.

== Predict

The `spa` client in your realm requires the PKCE method `S256`. The starter
turns PKCE off. If you rolled out the starter as it is, what would happen when
a user signs in? Write it down.

.Answer
[%collapsible]
====
Keycloak would refuse the sign-in in the popup with an error page, because the
request has no code challenge and the client requires one. The server side of
PKCE is already enforced; the app has to do its half.
====

== Code: fix the starter

. Run the task **Test the d3-spa-pkce/frontend starter**. The first run
  installs the dependencies. The tests fail: they find PKCE off, tokens
  written to `localStorage`, and an expired token handed to the API.
. Open `d3-spa-pkce/frontend/starter/src/auth.ts` and fix the three places
  marked `ANTI-PATTERN`:
.. Remove `disablePKCE: true`. With nothing set, `oidc-client-ts` uses PKCE
   with `S256` for every sign-in.
.. Keep the user and the sign-in state in memory: give `userStore` and
   `stateStore` a `WebStorageStateStore` over an `InMemoryWebStorage`, which
   you import from `oidc-client-ts`.
.. In `accessToken()`, when the token expires within 30 seconds, call
   `refresh()` first and return the new token. `user.expires_at` is the expiry
   in seconds since 1970.
. Run the test task again until every test passes.
+
.Reference solution
[%collapsible]
====
[source,typescript]
----
import { UserManager, WebStorageStateStore, InMemoryWebStorage, type User } from 'oidc-client-ts';

    // in the UserManager settings, with disablePKCE removed:
    userStore: new WebStorageStateStore({ store: new InMemoryWebStorage() }),
    stateStore: new WebStorageStateStore({ store: new InMemoryWebStorage() }),

export async function accessToken(): Promise<string | null> {
  if (!manager || !user) return null;
  const expiry = user.expires_at ?? 0;
  if (expiry * 1000 - Date.now() < 30_000) {
    const refreshed = await refresh();
    return refreshed?.access_token ?? null;
  }
  return user.access_token;
}
----

`refresh()` already shares one refresh between concurrent calls, so two API
calls at the same moment cause one token request, not two.
====

== Explain

. A script injected into the page cannot read `localStorage` any more. Is the
  SPA's token now safe from it?
+
.Answer
[%collapsible]
====
No. The script runs in the same page, so it can call the app's own functions
or wrap `fetch` and capture the `Authorization` header. Memory storage shrinks
the window: nothing survives the tab, and no other tab can read it. Preventing
cross-site scripting (XSS) and keeping tokens short-lived are still the SPA's
main defenses.
====
. Why does the SPA refresh 30 seconds early instead of waiting for a 401?
+
.Answer
[%collapsible]
====
A request sent with a token that expires on the way is refused, and the user
sees an error for something the app could have prevented. Refreshing a little
early also covers small clock differences between the browser and the API.
====

== At your desk

The SPA's whole Keycloak setup, with `oidc-client-ts`:

[source,typescript]
----
new UserManager({
  authority: config.issuer,
  client_id: config.spaClientId,
  redirect_uri: `${origin}/auth/popup-callback`,
  response_type: 'code',                 // PKCE (S256) is on unless you disable it
  userStore: new WebStorageStateStore({ store: new InMemoryWebStorage() }),
  stateStore: new WebStorageStateStore({ store: new InMemoryWebStorage() }),
});
----

Check the client too: public, standard flow only, PKCE `S256` required, exact
redirect addresses, and a short access-token lifetime.
