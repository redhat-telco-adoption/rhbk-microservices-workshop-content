= Build secure microservices with Red Hat build of Keycloak
:navtitle: Welcome

Welcome to the developer track of this hands-on lab. Your operations team
already runs Red Hat build of Keycloak, called Keycloak from here on, and has
prepared a realm for you. You work on the application side: how three kinds
of browser app obtain and use tokens, how an application programming
interface (API) validates them, and how services call each other safely.

You write code. Most modules give you a copy of one of the lab's services with
a security check removed or broken on purpose. You fix it, prove the fix with
unit tests that need no cluster, then build and roll it out to your own
OpenShift namespace and check it against the live system.

== What you will be able to do

By the end of the lab you can:

* read an access token and explain where each claim comes from;
* connect an application to a Keycloak realm, and recognize an issuer that is
  almost right from its error;
* write the sign-in code of a browser single-page application (SPA) that uses
  Proof Key for Code Exchange (PKCE) and keeps tokens in memory;
* make the six checks every API owes every token, in Java, Python, and
  JavaScript, and tell 401 from 403;
* protect a backend for frontend (BFF) against leaking credentials and against
  cross-site request forgery (CSRF);
* choose between token exchange and client credentials for a call to another
  service, and implement both;
* ask operations for exactly the client a new application needs, and wire the
  application to it.

== How each module works

Most activities follow the same loop:

[cols="1,4"]
|===
|*Why it matters* |The failure or attack the code prevents.
|*Predict* |Write down what you expect before you look.
|*Code* |Fix the starter. The tests tell you when it is right.
|*Ship it* |Build and roll out your code to your own namespace.
|*See it* |Look at the token, the cookie, the trace, or the log.
|*Break it* |Run something broken on purpose and read the error.
|*Explain* |Answer a question; open the answer to compare.
|*At your desk* |The code or checklist item to take home.
|===

Answers and reference solutions are hidden behind a click so you can try
first.

== The application

Orders is the protected API. It allows reads to users with the `user` role and
writes to users with the `manager` role. When it creates an order, it calls
Inventory on the user's behalf and Notifications as itself.

The same browser frontend is served three ways, once per sign-in pattern:

* **SPA:** the browser signs in and calls Orders with an access token it keeps
  in memory.
* **BFF:** a server signs in for the browser, keeps the tokens, and gives the
  browser only a session cookie.
* **Reverse proxy:** a gateway in front of the app signs the user in, keeps the
  tokens, and adds the token to API calls.
