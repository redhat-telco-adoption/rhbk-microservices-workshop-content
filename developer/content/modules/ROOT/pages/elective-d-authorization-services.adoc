= Elective D: Authorization Services
:navtitle: D. Authorization Services

*Time:* 40 minutes +
*Before you start:* Module 6, and the terminal setup from xref:electives.adoc#_the_terminal[Electives] +
*By the end, you can:* read a resource, policy, and permission model in Keycloak; ask Keycloak for a decision on a user's behalf, with and without pushed claims; configure a policy enforcer and a Claim Information Point (CIP) that only trusts facts the user cannot set

== Why it matters

So far each API decides with roles from the token: `manager` may create
orders. Real rules are often finer: *a manager may approve an order only for
their own region, and only from a branch office*. That rule depends on an
attribute of the user (their region) and on facts about the request that the
token does not contain (where it came from). This is attribute-based access
control (ABAC).

Keycloak Authorization Services can hold such rules centrally. Your API, the
*resource server*, describes what it protects (resources and scopes),
operations writes *policies*, and *permissions* combine them. The API asks
Keycloak for a decision and can *push claims*, facts from the request or from
other systems, for the policies to use. The component in your API that
collects those facts is the CIP.

== Check first: has operations set it up?

Authorization Services is not part of your realm's standard preparation. In
the
link:{keycloak_origin}/admin/master/console/#/{realm_name}[Keycloak administration console,window=_blank],
open **Clients → orders-api**. If it has an **Authorization** tab, operations
has set up the model below for your realm: do every section. If it has none,
read the model, skip the sections marked *(live)*, and do the others; the
policy enforcer section needs no Keycloak changes.

== See it: the model operations configured

The model protects one resource, `order`, with two scopes, `order:read` and
`order:approve`:

[cols="1,1,3",options="header"]
|===
|Kind |Name |What it says
|Policy (Role) |`is-manager` |The user has the realm role `manager`.
|Policy (Role) |`is-user` |The user has the realm role `user`.
|Policy (Regex) |`region-north` |The token's `region` claim is `north`. The `manager` user has that attribute, and a `region` scope puts it in `spa` and `orders-api` tokens.
|Policy (Regex) |`from-branch` |The pushed claim `channel` is `branch`. It is a *context attribute*: sent with the request, not read from the token.
|Permission |`read-order` |`order:read` needs `is-user`.
|Permission |`approve-order` |`order:approve` needs `is-manager`, `region-north`, and `from-branch`, all of them (*Unanimous*).
|===

*(live)* On **Clients → orders-api → Authorization**, open **Resources**,
**Policies**, and **Permissions**, and find each row of the table.

**Predict:** a manager asks to approve an order. Without anything pushed,
permit or deny?

== Do: ask Keycloak for a decision (live)

An API asks with the User-Managed Access (UMA) grant, the protocol behind
Authorization Services, at the token endpoint. `response_mode=decision`
returns only the verdict.

. In the link:{spa_url}[SPA,window=_blank], sign out, sign in as `manager` (so
  the token carries `region`), and click **View orders**. Copy the token and
  run `paste_token`. It expires after five minutes; if a response is not the
  one a step describes, copy a fresh token.
. Ask as Orders, with its own credentials, on behalf of the user
  (`subject_token`), without pushed claims:
+
[source,bash]
----
decide() {
  as_orders_api -d grant_type=urn:ietf:params:oauth:grant-type:uma-ticket \
    -d audience=orders-api -d subject_token="$TOKEN" \
    -d 'permission=order#order:approve' -d response_mode=decision "$@" \
    "$ISSUER/protocol/openid-connect/token"; echo
}
decide
----
+
Keycloak answers with an `access_denied` error: `from-branch` had nothing to
match.
. Push the `channel` claim. Pushed claims are a base64-encoded JSON object
  whose values are arrays of strings:
+
[source,bash]
----
CLAIMS=$(printf '{"channel":["branch"]}' | base64 -w0)
decide -d claim_token="$CLAIMS" -d claim_token_format=urn:ietf:params:oauth:token-type:jwt
----
+
Keycloak answers with `{"result":true}`.

== Break it: who may push claims (live)

Pushing `channel=branch` from your terminal made you look like a branch
office. Could the browser do the same?

. Read the request the SPA would send, with the user's token as a bearer
  credential and no client secret:
+
[source,bash]
----
curl -s -H "Authorization: Bearer $TOKEN" \
  -d grant_type=urn:ietf:params:oauth:grant-type:uma-ticket \
  -d audience=orders-api -d 'permission=order#order:approve' -d response_mode=decision \
  -d claim_token="$CLAIMS" -d claim_token_format=urn:ietf:params:oauth:token-type:jwt \
  "$ISSUER/protocol/openid-connect/token"; echo
----
. **Predict:** will Keycloak accept it? Write it down, then run it.
+
.What happened
[%collapsible]
====
Keycloak refuses: public clients may not push claims. A browser application
cannot keep a secret, so anything it pushes could be forged. Only an
authenticated, confidential client, normally the resource server itself, may
push claims, and it is then responsible for their truth.
====
. Sign out of the SPA, and run `unset TOKEN CLAIMS`.

== Do: configure a policy enforcer

In an application, the Keycloak policy enforcer does what `decide` did by
hand: it maps request paths to resources and scopes, collects claims through
its CIP, and asks Keycloak for the decision before your code runs. Orders has
no approve endpoint yet. Write the configuration a Quarkus version of Orders
would use, with `quarkus-keycloak-authorization`, for this endpoint:

* `POST /orders/<id>/approve` needs scope `order:approve` on resource `order`.
* `channel` comes from the `X-Network-Zone` header, which the cluster's
  gateway sets on every request and removes when a browser sends it.

Write your version in a scratch file in the workspace, then compare.

.Reference configuration
[%collapsible]
====
[source,properties]
----
quarkus.keycloak.policy-enforcer.enabled=true
quarkus.keycloak.policy-enforcer.paths.approve.name=order
quarkus.keycloak.policy-enforcer.paths.approve.paths=/orders/{id}/approve
quarkus.keycloak.policy-enforcer.paths.approve.methods.post.method=POST
quarkus.keycloak.policy-enforcer.paths.approve.methods.post.scopes=order:approve
# The CIP: a claim from a header your gateway sets, never one the browser sets.
quarkus.keycloak.policy-enforcer.paths.approve.claim-information-point.claims.channel={request.header['X-Network-Zone']}
----

The enforcer needs the client's credentials to ask for decisions, from the
same Secret as today. Without the gateway's guarantee, the CIP line would let
any caller claim to be a branch office.
====

== Check

* Your policy enforcer configuration maps the approve endpoint to `order` and
  `order:approve`, and takes `channel` only from the gateway's header.
* If operations set up the model: `decide` was denied without pushed claims
  and returned `{"result":true}` with them, and the request without a client
  secret was refused.

== Explain

. If Orders pushed `channel`, where should it get that value from?
+
.Answer
[%collapsible]
====
From a source the user cannot set: the network zone a gateway or mutual
Transport Layer Security (TLS) connection established, a device-management
system, or Orders' own records. Never from a request header or body field the
browser controls. A CIP is only as trustworthy as its inputs.
====
. Why put the `approve-order` rule in Keycloak instead of in Orders' code?
+
.Answer
[%collapsible]
====
The rule can be reviewed, tested, and changed by the people responsible for
access policy, without a release of Orders, and several services can share
it. The cost is a Keycloak call per decision (cacheable) and a policy model
your team must learn. Coarse checks that rarely change, such as "needs
`user`", are simpler as roles in the token.
====

== At your desk

Choosing where authorization lives:

[cols="1,2",options="header"]
|===
|Rule |Where
|"Needs the `user` role" |Role in the token, checked locally by the API
|"Only the owner may change this order" |The API's own code, which knows the order's owner
|"Managers in the order's region, from a branch, during business hours" |Authorization Services, or a policy engine you already run
|===
