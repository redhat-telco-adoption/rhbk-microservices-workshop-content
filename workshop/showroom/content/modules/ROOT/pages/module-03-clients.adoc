= Module 3: Configure clients, roles, and audiences
:navtitle: 3. Clients and tokens

== Know

An OIDC client describes an application. Public browser clients cannot keep a
secret; confidential server-side clients can. Authorization code with PKCE
protects the browser login flow. Exact redirect URIs prevent a token response
from being sent to an untrusted callback. An audience identifies the API that
should accept a token.

== Do: create the browser client

. In your realm, create an enabled OpenID Connect client named `spa`.
. Set client authentication **Off** and enable Standard flow. Keep implicit and
  direct access grants disabled.
. Set the valid redirect URI to `{spa_url}/auth/popup-callback` and Web Origin
  to the exact SPA origin (scheme and host only).
. Require PKCE with `S256` where the client configuration exposes the setting.
. Save, then check that a URL on another host is not in the redirect allowlist.

== Do: configure server-side clients

. Create a confidential `bff` client with Standard flow, PKCE `S256`, and the
  exact callback `{bff_url}/login/oauth2/code/keycloak`.
. Create a confidential `proxy` client with Standard flow, PKCE `S256`, and
  the exact callback `{proxy_url}/oauth2/callback`.
. Create a confidential `orders-api` client with service accounts enabled and
  browser flows disabled. Keep its generated secret in your own namespace.
. Create API resource clients named `inventory-api` and `notifications-api`.
  Do not enable user login flows for these resource clients.
. Add realm roles `user` and `manager`; make `manager` include `user`.
. Assign `user` to both users created in Module 2. Assign `manager` to the
  `manager` user as well.
. Add the `notifier` client role to `notifications-api` and assign it only to
  the `orders-api` service account.

== Do: constrain token audiences

Add audience mappers for `orders-api`, `inventory-api`, and
`notifications-api` in the client scopes or client configuration supported by
your RHBK version. Attach the resulting audiences to these clients:

[cols="1,3",options="header"]
|===
|Client |Audience assignment
|`spa`, `bff`, and `proxy` |`orders-api` only. Add `legacy-api` only if the facilitator confirms that optional service is available.
|`orders-api` |`notifications-api` by default; allow `inventory-api` only for the configured token-exchange flow.
|`verify-browser`, if provided |The same user-facing API audiences as `spa`.
|===

Do not give browser clients the `inventory-api` audience. Check the `proxy`
client explicitly; it needs the same `orders-api` audience as `spa` and `bff`.
Keep `notifications-api:notifier` on the `orders-api` service account only.

Configure standard token exchange so `orders-api` can exchange a user token for
`inventory-api`; do not permit arbitrary clients to exchange tokens. The
facilitator will point out the audience-mapper controls for the installed RHBK
version; preserve the exact client IDs and audience assignments above.

== Check

Confirm `iss` equals your realm issuer, the reader has the `user` role, and an
SPA access token has `orders-api` in `aud` without `inventory-api`. Use only a
facilitator-approved local inspector that displays selected claims and never
prints or saves the full token. If that tool is unavailable, ask the
facilitator to show the sanitized claim result. The direct Orders-token to
Inventory rejection is demonstrated in Module 6 unless the facilitator
provides the safe token matrix earlier.

**Expected:** browser clients use authorization code + PKCE; the confidential
clients have exact callback URIs; API tokens are audience-restricted.

== If something is wrong

Check for a missing scheme, path, or trailing slash in the redirect URI. Avoid
wildcard redirect URIs. If PKCE or token exchange controls are absent in your
console, ask the facilitator to confirm the installed RHBK version and provide
the corresponding UI path. Never paste a client secret into the guide or chat.
