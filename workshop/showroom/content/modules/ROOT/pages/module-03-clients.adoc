= Module 3: Configure clients, roles, and audiences
:navtitle: 3. Clients and tokens

== Know

An OIDC client describes an application. Public browser clients cannot keep a
secret; confidential server-side clients can. Authorization code with PKCE
protects the browser login flow. Exact redirect URIs prevent a token response
from being sent to an untrusted callback. An audience identifies the API that
should accept a token.

== Do: create clients

. In your realm, create an enabled OpenID Connect client named `spa`. Set it to
  **Public** (client authentication Off), Standard flow On, implicit flow and
  direct access grants Off. Require PKCE method `S256`.
. Set SPA's exact redirect URI to `{spa_url}/auth/popup-callback`, post-logout
  redirect URI to `{spa_url}/auth/logout-callback`, and Web Origin to
  `{spa_url}` (scheme and host only).
. Add each redirect URI, post-logout URI, and Web Origin to its list with the
  console's **+** control, then click **Save**. Confirm `spa` appears in the
  Clients list, reopen it, and verify it is enabled and Public, Standard flow
  is On, PKCE is `S256`, and the exact redirect URI, post-logout URI, and Web
  Origin persisted. If the client or a value is missing, resolve any visible
  validation message. If Save remains unresolved and no message explains why,
  stop and ask the facilitator; do not assume Save succeeded.
. Create confidential clients `bff` and `proxy`. For both, set Standard flow
  On, implicit flow and direct access grants Off, and PKCE `S256`. Set BFF's
  exact callback to `{bff_url}/login/oauth2/code/keycloak` and post-logout URI
  to `{bff_url}/`. Set proxy's exact callback to
  `{proxy_url}/oauth2/callback` and post-logout URI to `{proxy_url}/`.
. Create confidential `orders-api` with Standard flow Off, implicit flow Off,
  direct access grants Off, and service account On. Enable standard token
  exchange for this client only. Keep its generated secret private in your
  namespace.
. Create confidential resource clients `inventory-api` and
  `notifications-api`; keep Standard flow, implicit flow, direct access grants,
  and service accounts Off. Add client role `notifier` to `notifications-api`.

**Check:** `spa`, `bff`, and `proxy` have the exact callback and PKCE settings
above. Only `orders-api` has a service account and standard token exchange.
For `spa`, `bff`, `proxy`, and `orders-api`, check that the effective client
scopes retain the `roles`, `profile`, and `email` defaults. The roles mapper
adds role claims to tokens; role scope mappings separately limit which roles
the client may receive.

== Do: assign realm roles to learner users

. Create realm roles `user` and `manager`; configure `manager` to include
  `user` as a composite role.
. Assign `user` to both users from Module 2. Assign `manager` to the `manager`
  user as well.

Use the official RHBK 26.4 procedures for
link:https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/assigning_permissions_using_roles_and_groups#creating-a-realm-role[creating realm roles],
link:https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/assigning_permissions_using_roles_and_groups#converting-a-role-to-a-composite-role[converting `manager` to a composite role], and
link:https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/assigning_permissions_using_roles_and_groups#assigning-role-mappings[assigning role mappings]. Follow the documented procedures without assuming a different console path.

**Check:** the reader has realm role `user`; the manager has realm roles
`user` and `manager`.

== Do: limit client role scope mappings

Disable full-scope access on `spa`, `bff`, `proxy`, and `orders-api`. For these
clients, explicitly allow the realm roles `user` and `manager`. This limits
which already-assigned user roles can be included in a token; it does not
assign roles to the reader or manager.

== Do: assign the Orders service-account client role

Assign client role `notifications-api:notifier` only to the `orders-api`
service account. This is a client role for the workload identity, separate
from the users' realm roles.

**Check:** only the Orders service account has
`notifications-api:notifier`.

== Do: constrain token audiences

Create client scopes with Audience protocol mappers. Each mapper must add its
target client ID to the **access token** `aud` claim, not the ID token. Use
these exact scope, client, and assignment values:

[cols="1,2,3",options="header"]
|===
|Scope |Mapper audience |Assignment
|`orders-api-aud` |`orders-api` |Default on `spa`, `bff`, and `proxy`
|`notifications-api-aud` |`notifications-api` |Default on `orders-api`
|`inventory-api-aud` |`inventory-api` |Optional on `orders-api` only
|===

Add a separate Audience mapper for `proxy` itself to the proxy access token.
Do not give browser clients the `inventory-api` audience. Orders calls
Inventory using `scope=inventory-api-aud` and `audience=inventory-api` in its
configured token-exchange flow.

Legacy is excluded when the facilitator has not enabled it. Add
`legacy-api-aud` as a default scope on `spa`, `bff`, and `proxy` only when the
facilitator confirms that the Legacy API is available.

For the audience mapper procedure, see the official RHBK 26.4
link:https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/assembly-managing-clients_server_administration_guide#hardcoded-audience[Hardcoded audience section].
It describes creating an Audience mapper for a client scope and selecting the
included client audience. For attaching that scope as default or optional, use
the official RHBK 26.4
link:https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/assembly-managing-clients_server_administration_guide#link-client-scope-with-the-client[Link client scope with the client procedure].
To check effective scopes, use the
link:https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/assembly-managing-clients_server_administration_guide#evaluating-client-scopes[Evaluating Client Scopes procedure].

When adding the `orders-api` audience, `orders-api` should appear in the
**Included Client Audience** picker. If it is absent even though `orders-api`
appears in the realm's Clients list, stop and ask the facilitator to check the
console and realm state. Do not save an incomplete mapper or assume the scope
name adds an audience. Continue after the saved mapper and client-scope
evaluation show the intended audience in the access token.

For role scope mappings, see the official RHBK 26.4
link:https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/assigning_permissions_using_roles_and_groups#role-scope-mappings[Role scope mappings section].
Turn Full Scope Allowed Off and explicitly add only the intended roles. Keep
the `roles` client scope and its role mapper so configured roles can appear as
token claims; the scope mappings alone do not create role claims.

For enabling the Orders service account and assigning its client role, see the
official RHBK 26.4
link:https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/server_administration_guide/assembly-managing-clients_server_administration_guide#using-a-service-account[Using a service account procedure].
The guide describes enabling service accounts on the client and assigning
roles to its service account. Console labels and layout can vary by version;
confirm the installed UI with the facilitator rather than assuming a path.
Use the
link:https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.4/html/securing_applications_and_services_guide/token-exchange-[RHBK 26.4 token-exchange guide]
for standard token exchange and its scope/audience behavior. Follow the exact
settings in this module; if the installed console does not expose a required
setting, ask the facilitator to verify the version and control instead of
guessing a menu path.

== Check

Use only a facilitator-approved local inspector that displays selected
claims. Never print, screenshot, or save a full token. Confirm the SPA access
token has your realm issuer and `orders-api` in `aud`, and does not have
`inventory-api`. Confirm Orders has the default `notifications-api` audience
and can request the optional Inventory audience for token exchange. If the
approved inspector is unavailable, ask the facilitator to show the sanitized
claim result. The direct wrong-audience rejection is demonstrated in Module 6.

**Expected:** browser clients use authorization code plus PKCE; server-side
clients have exact callbacks; tokens contain only their intended audiences;
and the service account has only the machine role required for Notifications.

== If something is wrong

Check for a missing scheme, path, or trailing slash in a redirect URI. Avoid
wildcards. If a required flow, scope, role-mapping, or PKCE control is absent,
stop and ask the facilitator to verify the installed RHBK version and the
corresponding setting. Never paste a client secret into the guide or chat.
