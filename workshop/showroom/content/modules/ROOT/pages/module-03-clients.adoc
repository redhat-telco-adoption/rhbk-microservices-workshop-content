= Module 3: Configure clients, roles, and audiences
:navtitle: 3. Clients and tokens

== Know

An OIDC client describes an application. Public browser clients cannot keep a
secret; confidential server-side clients can. Authorization code with PKCE
protects the browser login flow. Exact redirect URIs prevent a token response
from being sent to an untrusted callback. An audience identifies the API that
should accept a token.

All steps below happen in the Keycloak administration console with your realm
`{realm_name}` selected in the realm list. Lists show 10 rows per page; once
you have more clients, users, or roles, type the name in the list's search box
instead of looking on page 1.

== Do: create clients

Create each client from **Clients → Create client**. The wizard has three
pages: **General settings** (client type OpenID Connect and the client ID),
**Capability config**, and **Login settings**. Click **Next** between pages and
**Save** on the last one. Leave every setting not listed here at its default.

[cols="1,3,3",options="header"]
|===
|Client ID |Capability config |Login settings
|`spa`
|Client authentication **Off**; Standard flow **On**; Direct access grants
**Off**; PKCE Method `S256`
|Valid redirect URIs `pass:a[{spa_url}/auth/popup-callback]`; Valid post logout
redirect URIs `pass:a[{spa_url}/auth/logout-callback]`; Web origins `pass:a[{spa_url}]`
|`bff`
|Client authentication **On**; Standard flow **On**; Direct access grants
**Off**; PKCE Method `S256`
|Valid redirect URIs `pass:a[{bff_url}/login/oauth2/code/keycloak]`; Valid post logout
redirect URIs `pass:a[{bff_url}/]`
|`proxy`
|Client authentication **On**; Standard flow **On**; Direct access grants
**Off**; PKCE Method `S256`
|Valid redirect URIs `pass:a[{proxy_url}/oauth2/callback]`; Valid post logout redirect
URIs `pass:a[{proxy_url}/]`
|`orders-api`
|Client authentication **On**; Standard flow **Off**; Direct access grants
**Off**; Service accounts roles **On**; Standard Token Exchange **On**
|none
|`inventory-api`
|Client authentication **On**; all flows **Off**
|none
|`notifications-api`
|Client authentication **On**; all flows **Off**
|none
|===

== Do: create realm roles and assign them

. Open **Realm roles → Create role**, enter `user`, and save. Do the same for
  `manager`.
. Open the `manager` role, go to its **Associated roles** tab, click **Assign
  role**, and choose **Realm roles** from its menu. Select `user` and click
  **Assign**. `manager` is now a composite role that includes `user`.
. Open **Users → reader → Role mapping → Assign role → Realm roles**,
  select `user`, and click **Assign**. For `manager`, assign `manager` (it
  includes `user`).
+
image::m03-role-mapping.png[Role mapping tab for the manager user]

**Check:** the reader's **Role mapping** tab shows `user`; the manager's shows
`manager` (and `user` when you clear **Hide inherited roles**). Both also show
Keycloak's own `default-roles-{realm_name}`.

Open **Clients → orders-api → Service accounts roles → Assign role → Client
roles**, select `notifications-api` `notifier`, and
click **Assign**. This is a
machine role for the Orders workload, separate from the users' realm roles.

== Do: limit which roles each client can receive

For each of `spa`, `bff`, `proxy`, and `orders-api`:

. Open **Clients →** _client_ **→ Client scopes →** _client_**-dedicated →
  Scope**.
. Turn **Full scope allowed** **Off**.
. Click **Assign role → Realm roles**, select `user` and `manager`, and click
  **Assign**.

For `orders-api` only, also click **Assign role → Client roles** and assign `notifications-api` `notifier`. With full scope off, the Orders service-account
token carries only the roles allowed here; without `notifier`, every manager
write later fails with a 502.

image::m03-dedicated-scope.png[Scope tab of orders-api-dedicated with user, manager, and notifier]

**Check:** `orders-api-dedicated` lists `user`, `manager`, and
`notifications-api notifier`; the other three list `user` and `manager`.

== Do: constrain token audiences

Create three client scopes, each with one Audience mapper:

. Open **Client scopes → Create client scope**. Enter the name, set **Type** to
  **None**, turn **Include in token scope** On (it starts Off), and save.
. On its **Mappers** tab choose **Configure a new mapper → Audience**. Enter the
  scope name as the mapper name, select the **Included Client Audience**, turn
  **Add to access token** On and **Add to ID token** Off, and save.
+
image::m03-audience-mapper.png[Audience mapper for orders-api-aud]

[cols="1,1,2",options="header"]
|===
|Client scope |Included Client Audience |Attach to
|`orders-api-aud` |`orders-api` |`spa`, `bff`, `proxy` as **Default**
|`notifications-api-aud` |`notifications-api` |`orders-api` as **Default**
|`inventory-api-aud` |`inventory-api` |`orders-api` as **Optional**
|===

Attach each scope from **Clients →** _client_ **→ Client scopes → Add client
scope**: select the scope, then choose **Add → Default** or **Add → Optional**.
Keep the exact scope names; Orders requests `inventory-api-aud` by name when it
exchanges a token. Do not give browser clients the `inventory-api` audience.

Finally, the proxy validates tokens issued to itself. Open **Clients → proxy →
Client scopes → proxy-dedicated → Configure a new mapper** (or **Add mapper →
By configuration**), choose **Audience**, name it `proxy-audience`, select
`proxy` as the Included Client Audience, turn **Add to access token** On, and
save.

Legacy is excluded when the facilitator has not enabled it. Add
`legacy-api-aud` as a default scope on `spa`, `bff`, and `proxy` only when the
facilitator confirms that the Legacy API is available.

== Check

Keycloak can show the token a client would receive. Open **Clients → spa →
Client scopes → Evaluate**, click the **Users** field and pick `reader` from
the list (typing alone does not select). Click **Effective role scope
mappings**, then **Generated access token**; the token appears only after
you switch tabs like this. Confirm:

* `iss` is `pass:a[{issuer}]`;
* `aud` includes `orders-api` and not `inventory-api`;
* `realm_access.roles` includes `user` but not `manager`.

Repeat for user `manager`: `realm_access.roles` includes `manager` and `user`.
After you change the user, switch tabs the same way so the token refreshes.
This view is for your own lab users only; do not copy or share the token.

image::m03-evaluate.png[Generated access token for reader on the spa client]

**Expected:** browser clients use authorization code plus PKCE; server-side
clients have exact callbacks; tokens contain only their intended audiences;
and the service account has only the machine role required for Notifications.

== If something is wrong

Check for a missing scheme, path, or trailing slash in a redirect URI. Avoid
wildcards. If `orders-api` is missing from the Included Client Audience list,
check that the `orders-api` client exists in your realm. Never paste a client
secret into the guide or chat.
