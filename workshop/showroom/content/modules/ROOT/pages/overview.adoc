= Overview
:navtitle: Overview

This workshop assumes you have used a web application with a login and know
what an HTTP request and a container are. You do not need to know OAuth or
OpenID Connect (OIDC) in advance; each module explains what it uses.

The facilitator provides a shared Keycloak server, one OpenShift namespace per
attendee with the applications already deployed, and shared logging and
tracing. You create and own your realm; nobody else can change it.

After the core path, five self-paced xref:electives.adoc[electives] cover
groups, signing-key rotation, token introspection, Authorization Services,
and tokens from other issuers, in about two and a half hours. Your environment
stays available after the session so you can finish them.

The times are estimates for a first run with people and will be adjusted after
a pilot.

== The application

Orders is the protected API. It allows reads to users with the `user` role and
writes to users with the `manager` role. When it creates an order, it calls
Inventory on the user's behalf and Notifications as itself.

The same browser front end is deployed three times, once per sign-in pattern:

* **SPA:** the browser signs in and calls Orders with an access token it keeps
  in memory.
* **BFF:** a server signs in for the browser, keeps the tokens, and gives the
  browser only a session cookie.
* **Reverse proxy:** a gateway in front of the app signs the user in, keeps the
  tokens, and adds the token to API calls.

== Definition of done

* Your realm signs users in to all three patterns.
* A reader can view orders but not create them, and a manager can create them,
  through every pattern.
* An order shows the user at Inventory and Orders' own identity at
  Notifications.
* Your capstone client passes its check.
* You can explain, for your own application, which pattern you would choose
  and which checks your API must make.
