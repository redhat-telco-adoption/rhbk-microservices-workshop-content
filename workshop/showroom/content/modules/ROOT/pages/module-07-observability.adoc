= Module 7: Operate it
:navtitle: 7. Operate it

== Why it matters

A secure design still has to be run: someone gets a 403 they did not expect, a
token ends up in a log, Keycloak has an outage. The evidence you have used so
far (traces, log lines with a reason, and tokens you can inspect) is what lets
you answer those calls quickly and without guessing. Each scenario below has a
reference answer; write yours first.

  and find the denied `POST /orders` trace. Through the BFF or proxy the trace
  is named after that app, for example `bff: POST orders-api`. The list does
  not mark it as an error; open it and click the Orders span to see the 403
  status. It never reaches Inventory or Notifications.
. In **Observe → Logs**, search for `missing_role` and click **Run Query**
  (again if the old results stay). The Orders line shows `decision` `deny`,
  status 403, and `reason` `missing_role`, with no token or secret in the log.
  A denied write through the BFF also has a BFF line with `roles: []`: the BFF
  logs its session's ID token, which carries no roles, while Orders checks the
  access token.

== Scenario 1: "I can't create orders"

A colleague signed in as `reader` says the app is broken: creating an order
fails. Using only the console and the logs, decide whether this is a bug or
policy, and what would change it.

.Reference answer
[%collapsible]
====
It is policy. The Orders log line says `status 403`, `reason missing_role`,
`roles ["user"]`. Authentication worked; the user lacks `manager`. The fix, if
the business agrees, is a role assignment in Keycloak, not a code change.
Before granting it, check the client side too: if the client's scope did not
include `manager`, the user could have the role and still not get it in the
token, as the service account did in Module 6.
====

== Scenario 2: a token appears in a support ticket

Someone pasted a request, including its `Authorization: Bearer ...` header,
into a ticket.

. **Try it.** Sign in to the SPA as `reader`, then in Keycloak open **Users →
  reader → Sessions** and sign out each session from its row menu.
. **Predict:** the user's sessions are gone. What will **View orders** in the
  SPA return now? Write it down, then click it.
+
.What happened
[%collapsible]
====
It still returns 200. Orders validates tokens locally with the realm's public
keys and never asks Keycloak whether the session still exists. The access
token stays valid until it expires, five minutes here.
====

What do you do about the ticket?

.Reference answer
[%collapsible]
====
. Treat it as an incident: restrict access to the ticket and remove the
  token from it and any copies.
. Find out what leaked. An access token expires on its own within minutes. A
  refresh token, session cookie, or client secret lasts much longer and is the
  real risk.
. End the user's sessions in Keycloak. That stops refresh and new tokens
  but, as you just saw, not an access token already issued.
. If a client secret leaked, regenerate it in Keycloak (**Credentials →
  Regenerate**) and update the Secret.
. Check logs for use of that identity during the exposure window.
. Prevent the next one: keep access tokens short-lived, and never log
  `Authorization` headers or cookies.
====

== Scenario 3: Keycloak is down for ten minutes

Complete row 5 of your Module 1 table: what happens to each pattern, and to an
order, while Keycloak is unreachable?

.Reference answer
[%collapsible]
====
* **Existing users keep working briefly.** APIs check signatures with keys
  they have already downloaded, so a valid access token keeps working until it
  expires (five minutes here). New sign-ins fail everywhere.
* **SPA:** when the token expires, the SPA cannot renew it and the user is
  signed out.
* **BFF and proxy:** same, at the next token refresh; the session cookie alone
  is not enough.
* **Orders:** reads keep working while the user's token is valid. Every
  *write* fails at once, because Orders exchanges a token with Keycloak for
  each Inventory call. Notifications would work until Orders' cached
  service-account token expires.

The design point: each call to Keycloak in a request path is a dependency.
Token exchange per request buys precise identity at the price of
availability. Run Keycloak highly available, and know which of your flows
depend on it per request.
====

== Do: a production review

Pick one application you work on. Write down, in one line each:

. Which pattern it uses, or should use, and why.
. Its redirect URIs and whether any contains a wildcard.
. The audience its tokens carry, and whether its APIs check it.
. Where its client secret lives and when it was last rotated.
. What it logs on a denial, and whether any log can contain a token.
. What happens to it during a Keycloak outage.

Compare your answers with the checklists in xref:at-your-desk.adoc[], then
discuss one gap with a neighbour or the facilitator: what would you change
first, and what would it take?
