= Module 1: The system and your predictions
:navtitle: 1. The system

== Why it matters

Signing in tells an application who you are. It does not decide what you may
do. That decision belongs to every API that receives a request, and each one
must check the token itself. Most real incidents in this area come from a
component that trusted something it should have checked: a button hidden in
the UI, a token meant for a different API, or a token kept where a script can
read it.

Where a token lives decides who can steal it. Before you build anything, you
will map where each pattern keeps its tokens and predict the consequences. You
check your predictions with real evidence in Modules 5 and 7.

== The pieces

* **Keycloak** authenticates users and issues tokens. An *access token* is a
  signed statement: who the user is, which application asked for it (`azp`),
  which APIs may accept it (`aud`), what roles it carries, and when it
  expires. Anyone holding it can use it until it expires.
* **Orders** is the protected API. It checks every token and decides.
* **Inventory** and **Notifications** are called by Orders, not by the
  browser.
* The **frontend** is one build deployed three times, once per sign-in
  pattern.

== Three kinds of token

A sign-in with OpenID Connect returns up to three tokens. Keep them apart;
mixing them up causes real bugs.

[cols="1,2,2",options="header"]
|===
|Token |What it is for |Who reads it
|*Access token* |Calling APIs. Short-lived (five minutes here). |The APIs. The app that holds it should only pass it along. (This lab's frontend decodes it to show you what is inside.)
|*ID token* |Telling the signing-in app who the user is: name, email, when they signed in. |Only the app that signed the user in. An API must never accept it.
|*Refresh token* |Getting a new access token without asking the user to sign in again. Longer-lived. |Only Keycloak. The app sends it back to Keycloak and never to an API; it must be kept as carefully as a password.
|===

All three are JSON Web Tokens (JWTs): three base64 parts separated by dots,
starting with `eyJ`, and signed by Keycloak. Signed means anyone can read
them and nobody can change them; never put secrets in claims.

== Explain

. Why does `orders-api` need a public Route, but `inventory-api` does not?
+
.Answer
[%collapsible]
====
In the SPA pattern the browser calls Orders directly, so Orders must be
reachable from the internet. Inventory and Notifications are only called by
Orders inside the cluster. Every API still validates tokens: being internal
reduces exposure, it does not replace authentication.
====

. Orders calls Inventory "on the user's behalf" and Notifications "as itself".
  What would go wrong if Orders simply forwarded the user's token to both?
+
.Answer
[%collapsible]
====
A forwarded token was issued for Orders, so Inventory would have to accept
tokens meant for another API. Any service holding a user's token could then
replay it anywhere. And Notifications would see a user identity for an action
that the system performs, not the user. Module 6 builds the two correct
alternatives.
====
