= Secure microservices with Red Hat Build of Keycloak
:navtitle: Welcome

Welcome to this hands-on lab. You will secure a small order system from an
empty Keycloak realm to a working, observable application: three ways to sign
users in to a browser app, an API that makes its own access decisions, and two
service-to-service calls with different identities.

You will not only follow steps. Each module asks you to predict what will
happen, look at the evidence (tokens, cookies, traces, and logs), and break
something on purpose so you recognize the error when you meet it in your own
work. You leave with a checklist and the code each application needs.

== What you will be able to do

By the end of the lab you can:

* choose between a browser single-page app (SPA), a backend-for-frontend (BFF),
  and a reverse proxy for a new application, and explain the tradeoff;
* register OIDC clients with the settings that matter and say why each one is
  set the way it is;
* connect an application to Keycloak with three or four configuration values;
* list the checks an API must make on every token, and find them in Java,
  Python, and JavaScript code;
* decide when a downstream call must carry the user's identity and when it
  should use its own;
* read a trace and a log line to tell an authorization denial from a
  configuration problem.

== How each module works

Most activities follow the same loop:

[cols="1,4"]
|===
|*Why it matters* |The failure or attack the setting prevents.
|*Predict* |Write down what you expect before you look.
|*Do* |Make the change. Every setting comes with its reason.
|*See it* |Look at the token, the cookie, the trace, or the log.
|*Break it* |Make one deliberate mistake and read the error.
|*Explain* |Answer a question; open the answer to compare.
|*At your desk* |The code or checklist item to take home.
|===

Answers are hidden behind a click so you can try first.
