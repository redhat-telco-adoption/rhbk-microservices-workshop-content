= Module 5: Prove where authorization happens
:navtitle: 5. Prove it

== Why it matters

A button the UI hides or disables protects nothing. Anyone can send the
request without the UI. The API that owns the data must decide on every
request, from the token alone. You will prove that here, and check your
Module 1 predictions about where each pattern keeps its tokens.

Two status codes matter:

* **401 Unauthorized** means the API does not know who you are: no token, an
  expired one, a forged one, or one meant for another API.
* **403 Forbidden** means the API knows who you are, and you are not allowed.

Telling them apart tells you where to look: 401 is usually configuration or
token handling, and 403 is usually role assignment.

You need the browser's developer tools for this module: press **F12** (or
**Cmd+Option+I** on a Mac). Use them only on your own lab apps.

=== Bypass the UI

The reader's write was refused. Is that the button's doing, or the API's?

. In the **Network** tab, right-click the `orders` request and copy the value
  of its `Authorization` header (it starts with `Bearer`).
. Open the **Console** tab. If the browser asks you to type `allow pasting`
  first, do so. Then paste this, putting your copied value between the
  quotes:
+
[source,javascript,subs="attributes+"]
----
const auth = 'Bearer ...';
const order = { item: 'widget', quantity: 1 };
await fetch('{orders_api_url}/orders', {
  method: 'POST',
  headers: { Authorization: auth, 'Content-Type': 'application/json' },
  body: JSON.stringify(order),
}).then((r) => r.status);
----
+
The result is `403`. No UI was involved: Orders read the `user` role from the
token and refused.
. Now remove the token and change one character of it:
+
[source,javascript,subs="attributes+"]
----
await fetch('{orders_api_url}/orders').then((r) => r.status);
await fetch('{orders_api_url}/orders', {
  headers: { Authorization: auth.slice(0, -4) + 'AAAA' },
}).then((r) => r.status);
----
+
Both return `401`. The forged one fails the signature check you saw in
Module 2.

Notice what you just did: you read the token and used it outside the app. A
malicious script on the page can do the same without you, for example by
wrapping `fetch` to capture the `Authorization` header, and send the token
anywhere. That is why an SPA keeps tokens short-lived and in
memory, never in `localStorage`, and why cross-site scripting (XSS) is the
SPA's main risk.

=== See it: the API's own record

Open **Observe → Logs** in the OpenShift Console, search for `missing_role`,
and click **Run Query** (again if the results do not change). Then search for
`invalid_token`. You find the Orders lines for your attempts:

* `"status":403`, `"reason":"missing_role"`, `"username":"reader"`,
  `"roles":["user"]`: Orders knew who you were and said no.
* `"status":401`, `"reason":"invalid_token"`: Orders could not establish who
  you were. (Orders reports a missing token as `invalid_token` too.)

No token appears in any line. The log records the decision, not the
credential.

== Do: the BFF

. Open your link:{bff_url}[BFF,window=_blank] and sign in as `manager`.
. Expand **Where session data is stored**: **Access token in JavaScript
  memory: No**, and the only cookie JavaScript can read is `XSRF-TOKEN`.

  ticked: JavaScript cannot read it, and it holds only a session ID. The

  carries a `Cookie` header and no `Authorization` header.

=== Break it: a request without CSRF protection

The browser attaches the session cookie to every request to the BFF, even one
started by another website. That is *cross-site request forgery* (CSRF). The
BFF therefore requires a second proof on every write.

. In the **Console**, send a write the way a forged request would, without
  the CSRF header:
+
[source,javascript]
----
await fetch('/api/orders', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ item: 'widget', quantity: 1 }),
}).then((r) => r.status);
----
+
The result is `403`, and Orders never sees the request.
. Click **Create a sample order** with **Network** open. The app's own request
  carries an `X-XSRF-TOKEN` header copied from the readable `XSRF-TOKEN`
  cookie. A page on another site cannot read that cookie, so it cannot forge
  the header.
. Sign out, sign in as `reader`, and confirm **View orders** succeeds and
  **Create a sample order** returns 403. Sign out.

== Do: the proxy

. Open your link:{proxy_url}[proxy,window=_blank] and sign in as `manager`.
  Keycloak's page appears at once because the whole app sits behind the
  proxy's sign-in.
. In **Application → Cookies**, find `_oauth2_proxy` (HttpOnly). JavaScript
  can read no cookies at all; **Where session data is stored** agrees.
. Send the same unprotected write from the **Console** as you did on the BFF.
  The proxy answers with its own `403 Forbidden` page before the request
  reaches Orders. The app's own button sends `X-Workshop-CSRF: 1`, which a
  page on another site cannot add to a cross-site request without the
  proxy's permission. This check is a rule in this lab's NGINX gateway
  configuration, not something oauth2-proxy provides. If you put a proxy in
  front of your own app, you must add an equivalent rule.
. Sign out, sign in as `reader`, and confirm 200 and 403. Sign out.

== Explain

. An attacker finds a cross-site scripting bug and runs JavaScript in each
  app. What can they do in the SPA that they cannot do in the BFF or proxy?
+
.Answer
[%collapsible]
====
In the SPA they can read the access token and send it to their own server,
then use it from anywhere until it expires. In the BFF and proxy there is no
token in the page to steal. They can still make requests from the victim's
open browser while the page is open, because those carry the session cookie
and the app's own CSRF proof. Cookie patterns shrink the damage; they do not
make XSS harmless.
====

. Why does the SPA not need CSRF protection?
+
.Answer
[%collapsible]
====
The SPA authenticates with an `Authorization` header that its own code adds.
Browsers never add that header automatically to a request from another site,
so a forged request arrives without credentials and gets 401.
====

. A user reports "403" after their account was moved to a new team. Where do
  you look first, and where would you look for "401"?
+
.Answer
[%collapsible]
====
403: the user's role assignments, and the client's role scope (an app whose
scope excludes a role never passes it on). The Orders log line shows exactly
which roles the token carried. 401: the token itself and configuration:
issuer, audience, expiry, clock skew, and whether the API can reach the
realm's keys.
====

== At your desk

Every API must make these checks on every request, in this order:

. **Signature**, with keys from the realm's `jwks_uri`, allowing only the
  expected algorithm (RS256 here).
. **Issuer** (`iss`) equals your realm's issuer exactly.
. **Audience** (`aud`) includes this API.
. **Expiry** (`exp`) is in the future, with a small clock tolerance.
. **Token type** is an access token, not an ID token.
. Only then, **roles** for the operation.

Orders (Spring Boot), `SecurityConfiguration.java` and `OrdersController.java`:

[source,java]
----
decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
    timestamps, new JwtIssuerValidator(issuer), typ, expiry, subject,
    new JwtAudienceValidator()));            // aud must contain "orders-api"

@PostMapping("/orders") @PreAuthorize("hasRole('manager')")
public Map<String, Object> createOrder(...) { ... }
----

Inventory (Python, PyJWT):

[source,python]
----
claims = jwt.decode(
    token, signing_key, algorithms=["RS256"], audience="inventory-api",
    issuer=ISSUER, leeway=30,
    options={"require": ["exp", "sub"]},
)
if claims.get("typ") != "Bearer":            # an access token, not an ID token
    raise AuthenticationFailure("invalid_token")
if "user" not in roles:
    raise AuthenticationFailure("missing_role", 403)
if claims.get("azp") != "orders-api":         # only Orders may call Inventory
    raise AuthenticationFailure("wrong_client", 403)
----

Notifications (Node.js, jose):

[source,javascript]
----
const jwks = createRemoteJWKSet(new URL(`${issuer}/protocol/openid-connect/certs`));
const verified = await jwtVerify(token, jwks, {
  issuer, audience: 'notifications-api', algorithms: ['RS256'], clockTolerance: 30,
});
const claims = verified.payload;
if (claims.typ !== 'Bearer' || !claims.exp || !claims.sub) status = 401;   // access tokens only
else if (claims.azp !== 'orders-api') status = 403;                         // only Orders may call
else if (!claims.resource_access?.['notifications-api']?.roles?.includes('notifier')) status = 403;
----
