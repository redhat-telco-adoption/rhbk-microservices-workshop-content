= Module 2: A realm is a trust boundary
:navtitle: 2. Realm

== Why it matters

A realm is a separate identity world inside one Keycloak server: its own
users, roles, clients, and signing keys. Every token a realm issues carries
the realm's address as its *issuer* (`iss`) and is signed with the realm's
private key. An API that trusts your realm checks both. A token from another
realm, even on the same server, fails those checks.

That is why the issuer is the single most important configuration value in
this lab. It tells every application where to find the realm's public keys and
which tokens to accept.

Your account can create a realm without being a Keycloak server administrator.
This is *delegated administration*: the `create-realm` permission lets you
create a realm and manage only the realms you create. Large organizations use
the same model to let teams own their realms without touching each other's.

== Do: create your realm

. Open the
  link:{keycloak_origin}/admin/master/console/[Keycloak administration console,window=_blank]
  and sign in with your username and password from xref:details.adoc[]. This
  account lives in Keycloak's `master` realm.
. In the left menu choose **Manage realms**, then **Create realm**. Enter the
  realm name `{realm_name}`, keep **Enabled** on, and click **Create**.
+
image::m02-create-realm.png[Create realm form]

. Keycloak switches to your new realm. Open **Manage realms** again: you see
  only `master` and your realm. You cannot see or change other attendees'
  realms.

== See it: the documents every application trusts

. Open **Realm settings** and, next to **Endpoints**, click **OpenID Endpoint
  Configuration**. This *discovery document* is public. Every application in
  this lab reads it at startup.
. Find these fields and note what each is for:
+
[cols="1,3",options="header"]
|===
|Field |What applications use it for
|`issuer` |The exact value every token's `iss` claim must match. It must be exactly `pass:a[{issuer}]`.
|`authorization_endpoint` |Where apps send the browser to sign in.
|`token_endpoint` |Where apps exchange a sign-in code, or their own credentials, for tokens.
|`jwks_uri` |Where APIs download the realm's public keys to check token signatures.
|`end_session_endpoint` |Where apps send the browser to sign out of Keycloak.
|===

. Open the `jwks_uri` address in a new tab. You see one or more public keys,
  each with a key ID (`kid`). Every token names the `kid` it was signed with,
  so an API can pick the right key without calling Keycloak for each request.

== Explain

. An attacker runs their own Keycloak and issues a token with
  `"realm_access": {"roles": ["manager"]}` and your realm's name in `iss`. Why
  does Orders reject it?
+
.Answer
[%collapsible]
====
The token is signed with the attacker's private key. Orders checks the
signature with the public keys from your realm's `jwks_uri`, and none of them
match. A correct-looking issuer string is not enough; the signature proves the
token came from your realm.
====

. Why do applications read the discovery document instead of having each
  endpoint configured by hand?
+
.Answer
[%collapsible]
====
One value, the issuer, gives them everything else. Keycloak can change
endpoint paths or rotate keys without every application being reconfigured.
It also means a wrong issuer breaks everything at once, which you will see in
Module 4.
====

== At your desk

* Use one realm per trust boundary (for example per product or per customer),
  not one per application. Applications that share users share a realm.
* Give teams delegated realm administration rather than server-wide admin.
* Treat the issuer as configuration that must be exact, including scheme,
  host, and the absence of a trailing slash.
