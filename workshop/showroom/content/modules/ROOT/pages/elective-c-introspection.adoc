= Elective C: Local validation or introspection
:navtitle: C. Introspection

== Why it matters

When a user's sessions end, Orders keeps accepting the tokens they already
hold (Module 7 shows this as an incident). Orders validates tokens *locally*: it checks the signature
with cached public keys and never asks Keycloak whether the session still
exists. That is fast and keeps working when Keycloak is briefly unreachable.

*Token introspection*, defined in Request for Comments (RFC) 7662, is the
alternative. The API sends the token
to Keycloak's introspection endpoint and asks whether it is still active. You
compare the two answers for the same token, then decide when each one is the
right choice.

Before you start, run the setup block from xref:electives.adoc#_the_terminal[Electives]
in the **Terminal** tab.

Steps 1–5 below must fit inside the token's five-minute lifetime. Read them
through first.

== Do: one token, two answers

. In the link:{spa_url}[SPA,window=_blank], sign out if you are signed in,
  sign in as `reader`, and click **View orders**. Copy the `Authorization`
  value of the `orders` request (the `GET`, not an `OPTIONS` preflight) from
  the **Network** tab, run `paste_token` in the terminal, and paste it.
. Ask Orders, which validates locally:
+
[source,bash]
----
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TOKEN" "$ORDERS_API/orders"
----
+
It prints `200`.
. Ask Keycloak, authenticating as the `orders-api` client:
+
[source,bash]
----
curl -s -u "orders-api:$ORDERS_SECRET" -d "token=$TOKEN" \
  "$ISSUER/protocol/openid-connect/token/introspect" | jq '{active, username, client_id, aud, exp}'
----
+
`active` is `true`, with the user, the client that obtained the token
(`spa`), and its audience.
. In Keycloak, open **Users → reader → Sessions** and sign out each session
  from its row menu.
. **Predict:** what will each command print now? Write it down, then run both
  again.
+
.What happened
[%collapsible]
====
Orders still returns `200`. Introspection returns only `{"active": false}`,
so the other fields `jq` asked for print as `null`. Keycloak knows the session is gone; Orders cannot know without
asking. If Orders prints `401`, the token expired; start again from step 1.
====
+
image::el-c-introspection.png[Terminal: Orders still returns 200 while introspection reports active false]

== Break it: who may ask

. Introspect with a wrong secret, printing only the status code:
+
[source,bash]
----
curl -s -o /dev/null -w '%{http_code}\n' -u 'orders-api:wrong' -d "token=$TOKEN" \
  "$ISSUER/protocol/openid-connect/token/introspect"
----
+
Keycloak refuses with `401`: only an authenticated client may introspect.
. Now consider the introspection answer from step 3 of the previous section.
  `orders-api` introspected a token that was issued to `spa`, and got the user
  back, because `orders-api` is in that token's `aud`. A client that
  authenticates but is not in the audience gets only `{"active": false}`, even
  for a live token, so `false` does not always mean revoked.
+
In production, give each introspecting service its own confidential client,
protect that client's secret like any other credential, and keep
introspection responses out of logs.

== Explain

. Orders handles a high volume of reads. Should it introspect every request?
+
.Answer
[%collapsible]
====
Usually not. Introspection adds a Keycloak call to every request, so latency
and Keycloak's availability become part of every read (recall Module 7's
outage scenario). Short access-token lifetimes plus local validation are the
common default. If you do introspect, cache the result for a short time, and
accept that the cache brings back a little of the delay you wanted to remove.
====
. Which operations would justify introspection?
+
.Answer
[%collapsible]
====
Operations where five minutes of a revoked user's access is too long: moving
money, changing account security settings, administrative actions. A common
design validates locally for everything and introspects only for those
operations, or at the gateway in front of them.
====
. Keycloak can issue *lightweight* access tokens, which omit most claims.
  How would an API that receives them make decisions?
+
.Answer
[%collapsible]
====
It cannot read roles from the token, so it must introspect to get them.
Lightweight tokens keep personal data and roles out of the browser and out of
logs that capture headers, at the price of an introspection call. The option
is **Always use lightweight access token** under a client's **Advanced**
settings.
====

== At your desk

[cols="1,2,2",options="header"]
|===
| |Local validation |Introspection
|Detects a revoked session |No; the token is valid until it expires |Yes, on the next call
|Keycloak in the request path |No; only for occasional JWKS downloads |Yes; every uncached request
|Works with opaque or lightweight tokens |No |Yes
|Secret needed by the API |None |A client secret for the introspection call
|===

Spring Security supports both models, but switching takes more than the
properties below. Local JWT validation starts from:

[source,yaml]
----
spring.security.oauth2.resourceserver.jwt.issuer-uri: ${ISSUER}
----

Introspection starts from:

[source,yaml]
----
spring.security.oauth2.resourceserver.opaquetoken:
  introspection-uri: ${ISSUER}/protocol/openid-connect/token/introspect
  client-id: orders-api
  client-secret: ${ORDERS_API_CLIENT_SECRET}
----

Orders defines its decoder in code, with audience and role checks, so these
properties alone do not change how it validates. With introspection you must
add those checks again: map the roles from the introspection response and
verify that `aud` contains `orders-api`.
