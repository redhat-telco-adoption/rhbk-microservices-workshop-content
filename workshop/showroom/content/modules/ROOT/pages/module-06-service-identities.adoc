= Module 6: Service-to-service identities
:navtitle: 6. Service identities

== Why it matters

Creating an order makes Orders call two other services, and they need
different kinds of authority:

* **Inventory** reserves stock *for the user*. It should know which user, and
  that the request came through Orders.
* **Notifications** sends a message that the *system* decided to send. No user
  asked for it directly.

Forwarding the user's token is the tempting shortcut, and it is wrong for
both. The token's audience is Orders, so Inventory would have to accept tokens
meant for someone else, and a leaked token would work everywhere. Notifications
would record a user for an action the user never took.

OAuth has a tool for each case:

* **Token exchange.** Orders hands the user's token to Keycloak and gets a new
  one: same user, audience `inventory-api`, and `azp` (the authorized party)
  `orders-api`. Inventory checks both. Keycloak allows the exchange only
  because the user's token lists `orders-api` in its `aud` (from Module 3): a
  client may exchange only tokens that were issued for it. When an exchange
  fails in your own work, check this first.
* **Client credentials.** Orders signs in as itself with its own secret and
  gets a token for its *service account*. That account has exactly one
  permission: the `notifier` role on Notifications.

You will set these up one piece at a time and use traces and logs to find
each missing piece, which is how you would debug them in your own work.

Right now a manager's order fails with 502. Keep the
link:{spa_url}[SPA,window=_blank] open and signed in as `manager`; you will
click **Create a sample order** after each step.

== Step 1: token exchange for Inventory

. In Keycloak, open **Clients → orders-api**. Under **Capability config**,
  turn **Standard Token Exchange** **On** and click **Save**.
. Create a client scope `inventory-api-aud` as in Module 3: **Type** **None**,
  **Include in token scope** On, and an **Audience** mapper with
  `inventory-api` as the Included Client Audience (access token On, ID token
  Off).
. Open **Clients → orders-api → Client scopes → Add client scope**, select
  `inventory-api-aud`, and choose **Add → Optional**. *Optional* means it is
  added only when Orders asks for it by name, which it does during the
  exchange. Ordinary tokens never carry the Inventory audience.
. Open **Clients → orders-api → Client scopes → orders-api-dedicated →
  Scope**, turn **Full scope allowed** **Off**, and assign the realm roles
  `user` and `manager`. The exchanged token now carries only the roles
  Inventory checks.
. **Predict:** will the order succeed now? If not, how far will it get?
  Write it down, then click **Create a sample order** in the SPA.

Check the response, then find out how far the request got.

. Open
  link:{openshift_console_url}/observe/traces?namespace=tracing&name=workshop&tenant={attendee_id}&start=15m&limit=100&q=%7B+resource.service.name+%3D+%22orders-api%22+%26%26+name+%3D+%22POST+%2Forders%22+%7D[your Orders traces,window=_blank]
  (**Observe → Traces**, Tempo instance `tracing / workshop`, Tenant
  `{attendee_id}`, Service Name `orders-api`, Max traces 100, and the link's query for `POST /orders` spans; only you can
  read this tenant, though the list names others). If you open Traces from the
  menu instead of the link, set those values yourself: the Tenant starts on
  `workshop`, which you cannot read. A trace can take a minute to appear:
  check that the newest `POST /orders` trace started after your click, and
  reload if it did not. Open it. It now contains an
  `inventory-api` span: the exchange worked. There is no `notifications-api`
  span.
. Open **Observe → Logs**, search for `/inventory/reserve`, and click **Run
  Query** (again if the results do not change). The newest Inventory line shows
  `"username": "manager"`, `"client_id": "orders-api"`, `"decision": "allow"`:
  the user's identity arrived, and Inventory can see that Orders brought it.
+
image::m06-inventory-log.png[Inventory log line for the manager, called by orders-api]
. Search for `/notify`. There is no line at all. Orders never reached
  Notifications, because it has no identity of its own yet.

== Step 2: a service account for Notifications

. Open **Clients → orders-api**. Under **Capability config**, turn **Service
  accounts roles** **On** and click **Save**. Orders can now request tokens
  for itself (the *client credentials* grant).
. Open **Clients → notifications-api → Roles → Create role**, enter
  `notifier`, and save. This is a *client role*: it belongs to Notifications
  and means nothing to any other API.
. Open **Clients → orders-api → Service accounts roles → Assign role → Client
  roles**, select `notifications-api` `notifier`, and click **Assign**.
+
image::m03-service-account-roles.png[Service accounts roles tab for orders-api]

. Create a client scope `notifications-api-aud` with an Audience mapper for
  `notifications-api`, and add it to `orders-api` as **Default**.
. **Predict:** Orders now has its own identity, and its service account has
  `notifier`. Will the order succeed? Write it down, then create an order.

Check the response, then search the logs for `/notify` again:

----
"status":403, "decision":"deny", "reason":"missing_role",
"username":"service-account-orders-api", "client_id":"orders-api", "roles":[]
----

image::m06-notify-denied.png[Notifications log line refusing the Orders service account]

Orders reached Notifications with its own identity, and Notifications refused
it. The service account has `notifier`, yet the token carried no roles.

.Why are the roles empty?
[%collapsible]
====
In Step 1 you turned **Full scope allowed** off for `orders-api` and allowed
only `user` and `manager`. That limit applies to every token issued to
`orders-api`, including its own service-account token. A role that is assigned
but not in the client's scope never reaches the token.
====

== Step 3: allow the role, then refresh the token

. Open **Clients → orders-api → Client scopes → orders-api-dedicated → Scope →
  Assign role → Client roles**, select `notifications-api` `notifier`, and
  click **Assign**.
+
image::m03-dedicated-scope.png[Scope tab of orders-api-dedicated with user, manager, and notifier]

. **Predict:** the scope now allows `notifier`. Will the next order succeed?
  Write it down, then create an order.
+
.What happened
[%collapsible]
====
It still fails. Orders reuses its service-account token until it expires (five
minutes here), so it is still sending the old one without `notifier`.
====
. Restart the `orders-api` rollout in the OpenShift Console (or wait five
  minutes), then create an order. It returns **201**: `reserved for manager`
  and the notification accepted. The first order after a restart can take a
  few seconds while Orders fetches the realm's keys and its first tokens.

If it fails with `Token exchange rejected` in the Orders log after a restart,
check that the new pod really started (Module 4) and that the `orders-api-client`
Secret has the current client secret.

Remember this one. After you change a service's roles, it keeps working with
its old permissions until it gets a new token.

== Explain

. Inventory checks `azp` is `orders-api`. What attack does that stop?
+
.Answer
[%collapsible]
====
Any other client that obtained an Inventory-audience token for a user, for
example by its own token exchange, would be refused. Inventory accepts the
user only when Orders is the one asking, so the path into Inventory is a
reviewed decision, not anything that can get a token.
====

. A reader somehow calls Orders' create endpoint. Could Orders' service account
  be used to reserve stock on their behalf?
+
.Answer
[%collapsible]
====
No. Orders checks the user's `manager` role before it calls either service.
And Inventory receives the user's own exchanged token, so it sees the reader's
roles, not the service account's. That is the point of keeping the user's
identity on calls made for the user.
====

. When would you use client credentials for a call made for a user?
+
.Answer
[%collapsible]
====
Only when the downstream action is genuinely the system's, such as sending a
notification, writing an audit event, or a scheduled job, and the downstream
service does not make decisions about the user. If the downstream service must
know or check the user, use token exchange.
====

== At your desk

Token exchange in Orders (`InventoryClient.java`), a plain HTTP form post to
the token endpoint:

[source,java]
----
form.add("grant_type", "urn:ietf:params:oauth:grant-type:token-exchange");
form.add("subject_token", subject.getTokenValue());
form.add("subject_token_type", "urn:ietf:params:oauth:token-type:access_token");
form.add("scope", "inventory-api-aud");
form.add("audience", "inventory-api");
form.add("client_id", "orders-api");
form.add("client_secret", clientSecret);
----

Client credentials in Orders, with Spring Security doing the token request and
caching (`application.yml` and `NotificationsClient.java`):

[source,yaml]
----
spring.security.oauth2.client.registration.notifications-api:
  client-id: orders-api
  client-secret: ${ORDERS_API_CLIENT_SECRET}
  authorization-grant-type: client_credentials
----

[source,java]
----
var authorized = manager.authorize(OAuth2AuthorizeRequest
    .withClientRegistrationId("notifications-api").principal("orders-api-machine").build());
headers.setBearerAuth(authorized.getAccessToken().getTokenValue());
----

[cols="1,1,1",options="header"]
|===
| |Token exchange |Client credentials
|Who is the subject |The user |The service itself
|Use when |The downstream service decides about the user |The action belongs to the system
|Keycloak setup |Standard Token Exchange on the caller; target audience as an optional scope |Service account on the caller; target's client role; target audience as a default scope
|Watch out for |Exchanges add a Keycloak call per request |Cached tokens keep old roles until they expire
|===
