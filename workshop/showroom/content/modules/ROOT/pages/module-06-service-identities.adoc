= Module 6: Compare login and service identities
:navtitle: 6. Identity paths

== Know

The SPA, BFF, and proxy are three ways to handle the same user-facing login.
They differ in where tokens live and how the browser calls an API. The
downstream calls demonstrate two distinct grants:

* **Token exchange:** Orders exchanges a user token for an Inventory-audience
  token. The user identity remains available, while the API checks that the
  authorized client is `orders-api`.
* **Client credentials:** Orders obtains a machine token for Notifications.
  There is no end-user identity; the service account has only the
  `notifier` client role.

== Do

. Sign in as `manager` in any of the three apps and click **Create a sample
  order**. The response shows the Inventory reservation (`reserved for
  manager`) and the accepted notification. This one request triggers both
  downstream calls.
. Open link:{openshift_console_url}/observe/traces?namespace=tracing&name=workshop&tenant={attendee_id}&start=15m&limit=100&q=%7B+resource.service.name+%3D+%22orders-api%22+%7D[your Orders traces,window=_blank] in the OpenShift Console
  (**Observe → Traces**, your own tenant `{attendee_id}`, service `orders-api`).
  Only you can read this tenant. Open the most recent `orders-api: POST /orders`
  trace. It shows one request crossing Orders, Inventory,
  and Notifications. The `orders-api: POST` spans with no other service below
  them are Orders' calls to Keycloak's token endpoint: the token exchange and
  the client-credentials request. Click one to see the Keycloak URL.
+
image::m06-trace.png[Trace of a manager order across Orders, Inventory, and Notifications]

. Copy the **Trace ID** shown at the top right of the trace page. Open
  **Observe → Logs**, which shows only your namespace, search for that trace
  ID, and click **Run Query**. If the old results stay, click **Run Query**
  again or the refresh button. Scroll the results to
  see the lines from all three APIs. Compare their `username`, `client_id` (the token's
  `azp`), `roles`, and `decision` fields:
+
* **Orders:** `username` `manager`, `client_id` `spa` (or `bff`/`proxy`), roles
  `manager` and `user`, decision `allow`.
* **Inventory:** `username` still `manager`, but `client_id` `orders-api`.
  Orders exchanged the user's token for an Inventory token, so the user
  identity is kept and the caller is Orders.
* **Notifications:** `username` `service-account-orders-api` with role
  `notifier`. Orders used its own client credentials, so no end-user identity
  is involved.
+
Orders lines repeat `trace_id`, `span_id`, and `level`: the Java tracing agent
adds them to every log line, and the application writes its own copy.
+

== Check

Explain why the Notifications request cannot be attributed to `reader`, and
why an arbitrary client must not be allowed to exchange a token for Inventory.

**Expected:** user login differs from machine authentication; Inventory
receives the narrow exchanged user token, Notifications receives a narrow
service-account token.

== If something is wrong

If a downstream call fails, inspect only sanitized logs in your own namespace.
Check the configured issuer, the audiences in **Client scopes → Evaluate**,
`client_id`/authorized party, and the service-account role. A 502 on every
manager write usually means `orders-api-dedicated` does not allow
`notifications-api notifier` (Module 3). Do not expose full
tokens or secrets in logs or screenshots.
